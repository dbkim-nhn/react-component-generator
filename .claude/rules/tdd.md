# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 단계를 건너뛰거나, 순서를 바꾸거나, 예외를 스스로 만들지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 다루지 않는 부분에만 적용한다.

## 적용 기준

### TDD를 반드시 적용한다

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 처리, 외부 호출 래퍼)
- **유틸 함수**
- **버그 수정** (재현 테스트를 먼저 작성해 실패를 확인한 뒤 고친다)

### TDD가 불필요하다

- **타입 정의**
- **설정 파일**
- **순수 UI** (로직 없는 마크업/스타일)
- **SQL**

경계가 모호하면 적용한다. 불필요 대상인지 의심스럽다면 테스트를 쓰는 쪽이 비용이 적다.

## RED - GREEN - REFACTOR

### 1. RED

- **하나의 동작 = 하나의 테스트.** 테스트 하나에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. import 오류, 문법 오류, 오타로 인한 실패는 RED가 아니다. 테스트를 고쳐서 올바른 이유로 실패하게 만든다.

### 2. GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 분기, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두** 통과하는지 실행해서 확인한다.

### 3. REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 모든 테스트가 **green을 유지**해야 한다. 변경할 때마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 4. 반복

다음 동작에 대한 **RED로 돌아간다.** 요구사항이 끝날 때까지 사이클을 계속한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 임시 파일, 다른 브랜치 보관 모두 포함한다. 보고 베끼면 테스트가 코드를 따라가게 되어 TDD가 아니다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| "너무 단순해서 테스트 불필요" | 단순한 코드는 테스트도 단순하다. 비용이 거의 없다. 단순해 보여서 깨질 때 가장 늦게 발견된다. |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 이미 통과하는 코드를 확인할 뿐이라 실패를 본 적이 없다. 무엇을 검증하는지 알 수 없다. 대부분 추가되지 않는다. |
| "시간이 없다" | 테스트 없이 만든 코드는 디버깅과 회귀 수정에 더 많은 시간을 쓴다. 급할수록 안전망이 필요하다. |
| "삭제하면 낭비" | 이미 쓴 코드는 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 버릴 코드라면 테스트도 버리면 되므로 쓰는 비용 손해가 없다. |
