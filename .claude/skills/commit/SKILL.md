# commit

변경사항을 읽고, 의미 있는 단위로 나누어, 일관된 한국어 커밋 메시지로 남긴다. 사용자가 커밋을 요청한 것 자체가 승인이므로 별도 확인 없이 바로 커밋하고, 끝난 뒤 결과를 보고한다. 승인을 생략하는 만큼 2단계(분류)와 제외 규칙을 꼼꼼히 지켜서 잘못된 커밋이 생기지 않게 한다.

## 절차

### 1. 변경사항 분석

먼저 상태를 파악한다. 아래 명령을 한 번에 실행해도 된다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 이 저장소의 기존 메시지 스타일 참고
```

- 변경이 없으면(깨끗한 working tree) 그 사실만 알리고 끝낸다.
- git 저장소가 아니면 알리고 중단한다.
- untracked 파일은 diff에 나오지 않으므로 `git status`에서 확인하고, 필요하면 내용을 직접 읽어 성격을 파악한다.
- diff가 매우 크면 `git diff --stat`로 윤곽을 잡은 뒤 파일별로 확인한다.
- `git log`에 이미 따르는 규칙(스코프 사용, 말투 등)이 보이면 그 스타일을 우선한다.

### 2. 논리적 단위로 분류

하나의 커밋은 하나의 목적만 담아야 나중에 리뷰·되돌리기·검색이 쉽다. 변경 파일과 hunk를 목적별로 묶는다.

- 기능 추가, 버그 수정, 리팩터링, 설정/의존성 변경이 섞여 있으면 분리한다.
- 같은 목적을 위한 코드·테스트·문서 변경은 한 커밋으로 묶는다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 파일 단위로 가장 주된 목적의 커밋에 포함한다. (비대화형 환경에서는 `git add -p`가 동작하지 않는다.) 결과 보고에 이 사실을 남긴다.
- 변경이 작고 단일 목적이면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.

**커밋하면 안 되는 것을 걸러낸다.** `.env`, 키/토큰/인증서, 빌드 산출물, `node_modules`, 로그, 에디터 임시 파일이 변경 목록에 있으면 제외하고 사용자에게 알린다. 시크릿으로 보이는 값은 응답에 그대로 출력하지 말고 파일명만 언급한다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 - 필요할 때만>
```

| type | 쓰는 경우 |
|------|-----------|
| feat | 사용자에게 보이는 새 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조·가독성 개선 |
| chore | 빌드, 설정, 의존성, 문서, 기타 잡무 |

- 요약은 한국어로, 한 줄(대략 50자 안팎)로 쓰고 마침표는 붙이지 않는다. "무엇을 했는지"가 드러나게 쓴다. (예: `feat: 로그인 폼 유효성 검사 추가`)
- 왜 바꿨는지가 diff만으로 드러나지 않을 때만 빈 줄 뒤에 본문을 덧붙인다. 사소한 변경에는 본문이 없어도 된다.
- 위 네 가지에 딱 맞지 않으면(문서만 수정 등) 가장 가까운 type을 고른다. 문서·테스트·스타일 변경은 보통 `chore`에 해당한다. 단, 저장소의 기존 로그가 `docs:`, `test:` 등을 이미 쓰고 있다면 그 관례를 따른다.
- 파일명 나열이나 "여러 가지 수정" 같은 모호한 문구는 피한다.
- Co-Authored-By 등 추가 trailer는 시스템/사용자 지침에 있을 때만 붙인다.

### 4. 바로 커밋하고 결과 보고

승인을 기다리지 않고 계획한 순서대로 `git add <파일들>` → `git commit -m ...`을 실행한다. `git add -A`나 `git add .`는 의도치 않은 파일을 끌어들이므로 쓰지 않고, 파일을 명시해서 추가한다.

커밋 후 `git log --oneline -N`으로 결과를 확인하고 아래 형태로 짧게 보고한다. 사용자가 잘못된 점을 발견하면 이 보고로 바로 알아챌 수 있어야 한다.

```
커밋 완료 (총 N개)

1. feat: 로그인 폼 유효성 검사 추가 (abc1234)
   - src/components/LoginForm.tsx
   - src/utils/validate.ts
2. chore: eslint 규칙 업데이트 (def5678)
   - .eslintrc.json

제외한 파일: .env (시크릿 가능성)
```

- 사용자가 메시지나 분류를 고치라고 하면 아직 push 전인 직전 커밋에 한해 `git commit --amend` 또는 `git reset --soft`로 정리한다. 이때만 amend/reset을 허용한다.

## 하지 말아야 할 것

- `git push`, `--amend`, `--no-verify`, `reset --hard` 등은 사용자가 요청하지 않는 한 실행하지 않는다.
- pre-commit hook이 실패하면 우회하지 말고 실패 원인을 알리고, 고칠 수 있으면 수정한 뒤 새 커밋으로 다시 시도한다.
